# Mac–Android USB 副屏代码评审

日期：2026-09-12。来源：https://cnb.cool/ConfigCrate/android-usb-mac-display 。
评审基线：`auto/usb-display-58eb`，提交 `f1cfea4226ea8a6f3936e277285f9c8330b33ef7`。

## 结论

值得继续做，但当前是协议与应用架构骨架，不是可以交给普通用户使用的副屏 MVP。现版本不建议作为“已可用软件”发布到 GitHub。可以公开实验源码，但必须明确未完成 USB 链路、未验证 Mac 编译与真机性能。

文件数量、教程完整度、协议常量测试通过，均不能证明端到端投屏已经实现。本次没有修改产品源码，没有提交或推送远端，也没有创建 GitHub 仓库。

## 验证范围

- Windows 本地静态阅读 Swift、Kotlin、协议、流水线及文档。
- `node protocol/tests/check_consistency.js`：17 项常量一致性检查通过。
- `test_protocol.js` 的限时运行：前 11 项通过；第 12 项大帧重组在 15 秒内未完成，进程由超时机制终止。这是限时结果，不代表该测试一定失败或永久死循环。
- 此机器未检测到 Java、Android SDK/adb、Swift/macOS 工具链；未运行 Android 或 Mac 构建，没有 USB 真机、触摸、温控或延迟实测。
- 本次未作完整安全审计或依赖供应链审计。

## 阻塞项与缺陷

### P0：Mac USB 收发仍然是占位

`macos/Sources/USBDisplayCore/AOATransport.swift:48` 的设备发现直接返回 `nil`，`handshake()` 因而直接报无设备。Accessory 发现同样返回 `nil`，端点打开只有注释，`rawWrite()` 的实际提交被注释，读循环每轮读取空数组，底层请求辅助函数直接返回成功。

影响：目前不能通过 USB 建立真实连接，也不能传输画面。这不是兼容性小 bug，而是核心模块尚未实现。

建议：先实现一个可验证的 USB 字节往返与设备切换实验，再接编码和显示。若采用 adb USB 隧道加速首轮验证，必须明确它要求开启 USB 调试与安装 adb，不等同于面向普通用户的 AOA 即插即用方案。

### P0：VideoToolbox 调用存在静态可识别的编译阻塞

`H264Encoder.swift:47` 将 `outputHandler` 传给 `VTCompressionSessionCreate`，但官方创建接口使用 `outputCallback/refcon`；block `outputHandler` 是编码帧接口的参数。`:87` 使用的 `kVTCompressionPropertyKey_EnableLowLatencyRateControl` 也与官方符号不同；官方低延迟设置是 encoder specification key，应在创建时设置。

这是依据官方接口的静态判定，尚无实际 Mac 编译日志。需要在 Mac 上修正后执行 `swift build`，继续检查其他桥接和并发编译错误。

参考：[Apple 压缩会话接口](https://developer.apple.com/documentation/videotoolbox/vtcompressionsession-api-collection)、[低延迟编码器规格键](https://developer.apple.com/documentation/videotoolbox/kvtvideoencoderspecification_enablelowlatencyratecontrol)。

### P1：虚拟显示器动态调用方式不可靠；默认只有镜像

`VirtualDisplay.swift:110` 在类对象上检查和调用实例初始化方法；`:120` 还对 mode 类检查不相关的 descriptor 初始化 selector。`:145` 将标量 `displayID` 返回值作为对象处理，通用 setter 也没有区分标量、结构体和对象的调用 ABI。

建议：改为有明确方法签名的 Objective-C 桥接层，验证创建、分辨率、显示器坐标与销毁。私有 API 路线应标实验兼容性，不承诺所有 macOS 更新均兼容。

`usbdisplayctl/main.swift:18` 默认 `captureOnly`，会采集主屏；它是镜像，不是额外扩展桌面。两种模式须在 UI、文档和验收中分开。

### P1：Android 14 USB 授权路径会触发异常

`android/app/build.gradle.kts:14` 指定 targetSdk 34。`UsbDisplayActivity.kt:174` 创建 mutable PendingIntent，却只传 action、未限定 package/component。针对 Android 14 的应用在 Android 14+ 上走到该权限请求路径时，受系统限制会抛异常；自动授予权限的插入路径可能不经过这里。

建议：限定本应用 package/component，审查 PendingIntent mutability，并测试已授权、首次授权、拒绝后重试及取消授权。参考：[Android 14 官方行为变更](https://developer.android.com/about/versions/14/behavior-changes-14#security)。

### P1：时钟单位与窄化转换有崩溃/统计错误风险

`DisplayLinkSession.swift:165/278/292` 直接 `UInt32(mach_absolute_time() / 1000)`：Mach 返回硬件 ticks，不保证是纳秒；超出 UInt32 的直接转换还会触发运行时错误。编码耗时也混用了采集时间与未经转换的 Mach 时间。

Android 的 `pingSentUpstreamUs` 保存完整 Long，线上的 ping/pong 却只有低 32 位；`:279` 比较两者，系统 uptime 超过 32 位微秒范围后 RTT 将匹配不上。32 位微秒约每 71.6 分钟回绕；Mac 原始 tick 的回绕阈值则取决于 timebase。

建议：使用统一的单调时钟单位，完整保存本地时间，用独立序号关联 ping，并明确回绕策略。RTT、编码耗时、实际端到端显示延迟必须分开，不能相互替代。

参考：[Apple Mach 时间说明](https://developer.apple.com/library/archive/qa/qa1643/_index.html)。

### P1：帧发送并发与背压策略可能破坏协议

`FrameProtocol.swift:196–252` 的 seq 和分片发送没有同一层串行保护。视频编码回调、主循环心跳、收到 ping 的回复来自不同执行路径；控制消息可能插在同一视频 payload 的两片之间，接收方会按视频字节吞掉它。AOATransport 背压又直接清空缓冲，而不是只丢完整的非关键视频帧。

建议：同一串行发送队列负责 seq 和完整逻辑帧的发送；仅在帧边界丢可丢的视频，保留 CONFIG、IDR、控制消息和触摸释放事件，必要时请求新 IDR。补充“视频分片与心跳同时发送”的实际实现测试。

### P1/P2：Android 生命周期与触摸仍需补齐

- 重复 connect 前没有可靠关闭上一条 transport；未见拔线接收器；读线程 EOF 后没有完整连接状态/资源清理闭环。应测试重复插入、拔线、后台、恢复及 Surface 重建。
- decoder 配置/释放与 reader feed 分属不同线程，统计容器也跨线程访问，应统一解码线程与线程安全统计。
- 首次请求 IDR 早于 decoder 配置完成，首帧可能被丢；decoder 成功配置及 Surface 重建后应再请求 IDR。
- `VideoSurfaceView.kt:51` 计算 Matrix 但未应用，视觉等比显示没有完成，触摸却按 letterbox 换算。
- Mac 触摸映射未更新到实际显示器的坐标与尺寸，镜像、HiDPI、非零原点扩展屏需分别验证；鼠标按住后的移动还需产生拖拽事件。

这些为静态发现的风险或缺失，仍需真机复现与回归，不应宣称都已经产生了用户可见故障。

## 测试与发布工程

- `test_protocol.js:184` 每 7 字节执行一次 Buffer.concat，累计复制复杂度 O(n²)，3 MiB 测例会产生大量重复复制；应使用分块缓冲/游标，并在每次模拟 read 时消费，而不是先拼完大块再解析。
- JS 测试重写了一份协议模型，没有调用生产 Swift/Kotlin 实现；“三端常量一致”不意味着生产解析器和传输可用。
- `.cnb.yml` 注释提到 macOS 层，实际未配置 Mac 构建。完整 Android/APK 流水线只在 main push；当前功能在默认 feature 分支，不能推断这些 APK 阶段已成功运行。
- README 写 MIT，但基线未见 LICENSE 文件，公开前补齐并核查依赖许可。
- README 的 25ms、USB P50/P99 数字没有随附实测设备、方法或结果，不能当已达性能宣传。
- 公开 GitHub 前提供真实安装包、版本化更新说明、中文/英文说明、设备兼容矩阵、已知限制，并保留 https://configcrate.com 外链。

## 建议实施顺序与发布门槛

1. 在 Mac 上让 host 编译通过，Android 编译通过；增加这两项 CI gate。
2. 独立验证实际 USB 双向字节通信、权限与断线清理。
3. 先做单一固定分辨率镜像链路，证明采集→编码→USB→解码→显示可连续运行；不要对外称扩展副屏。
4. 补真正虚拟显示器与正确触摸映射，明确私有 API 限制。
5. 做首次授权/拒绝、20 次拔插、静止画面最后一帧、后台/恢复、Surface 重建、至少 30 分钟运行的实测；记录温控、CPU、丢帧和延迟测量方法。
6. 达到上述门槛后，再迁移 GitHub 并发布带有已知限制的 experimental 版本；稳定版还需更多机型验证。

核心需求有价值，但主要剩余工作是 USB/macOS 系统接口和真机验证，不是继续增加教程或外围功能。需要用户提供可测试的 Mac 与 Android 设备，才能确认修复后的端到端效果。
